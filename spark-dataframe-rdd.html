01

RDD, DataFrame, Dataset

Три абстракции и чем они отличаются по контролю и оптимизации.

Что спросят
  • Чем RDD отличается от DataFrame?
  • Что такое Dataset и есть ли он в PySpark?
  • Почему DataFrame обычно быстрее RDD?
Вопросы и ответы
RDD vs DataFrame?
RDD — низкоуровневый набор объектов без схемы: вы контролируете каждую операцию, но оптимизатор вам не помогает. DataFrame — таблица с именованными колонками и типами: Spark сам оптимизирует план через Catalyst и быстро работает через Tungsten.
Что такое Dataset?
Dataset — это DataFrame с типизацией на уровне языка (в Scala/Java). Он даёт безопасность типов на этапе компиляции, но при этом проходит через тот же Catalyst. В PySpark полноценного Dataset нет: динамическая природа Python мешает статической типизации, поэтому на практике работают с DataFrame.
Почему DataFrame быстрее?
Потому что операции не выполняются по одной в Python/JVM-объектах, а компилируются оптимизатором в единый физический план. DataFrame не поднимает объекты JVM на каждый элемент и опирается на оптимизации Catalyst и Tungsten.
  • RDD — когда нужен точный контроль и нет структурной операции.
  • DataFrame — по умолчанию для любых табличных задач.
  • Dataset — типизированный вариант для Scala/Java, с теми же оптимизациями.
Вывод составителяПростой ответ на интервью: «DataFrame — это RDD со схемой и оптимизатором сверху». Всё дальнейшее — детали про Catalyst, Tungsten и цену UDF.
02

Схемы и типы

Зачем явная схема и что даёт тип данных колонки.

Что спросят
  • Что такое схема DataFrame?
  • Зачем задавать схему явно при чтении?
  • Что будет, если Spark угадывает типы?
Вопросы и ответы
Зачем явная схема?
Схема фиксирует имена и типы колонок. Явное задание избавляет от лишнего прохода по данным при inferSchema и предотвращает сюрпризы: например, телефон как строка не превратится в число, а дата не станет строкой.
Что даёт тип колонки?
Правильный тип позволяет оптимизатору применять эффективные операции и отсечение, экономит память (числа компактнее строк) и избавляет от ручных преобразований. Ошибки в типах — частая причина неверных результатов join и агрегаций.
Что не так с выводом типов?
inferSchema=true читает данные целиком, чтобы определить типы, — это дополнительная работа при старте. Хуже то, что он может ошибиться: ведущие нули в коде превратить в число, а NULL-подобные значения интерпретировать иначе, чем вы ожидали.
Пример
from pyspark.sql.types import (
    StructType, StructField, StringType, IntegerType, TimestampType
)

schema = StructType([
    StructField("user_id", IntegerType(), nullable=False),
    StructField("country", StringType(), nullable=True),
    StructField("amount", IntegerType(), nullable=True),
    StructField("created_at", TimestampType(), nullable=True),
])

df = spark.read.schema(schema).json("s3://bucket/events")

print(df.schema.simpleString())
# struct<user_id:int,country:string,amount:int,created_at:timestamp>
Вывод составителяХорошая привычка продакшена: схема задаётся явно и версионируется вместе с пайплайном. Это дешевле, безопаснее и стабильнее, чем надеяться на inferSchema.
03

Catalyst optimizer

Четыре фазы превращения запроса в физический план.

Что спросят
  • Что такое Catalyst?
  • Из каких фаз состоит оптимизация?
  • Какие типовые оптимизации он делает?
Вопросы и ответы
Что такое Catalyst?
Это оптимизатор запросов Spark на основе деревьев правил. Он принимает логический план (из DataFrame API или SQL) и превращает его в оптимизированный физический план.
Какие фазы у Catalyst?
1) Analysis — разрешение имён и типов. 2) Logical optimization — перестановка и упрощение правил. 3) Physical planning — выбор конкретных операторов (например, стратегии join). 4) Code generation — генерация Java-байткода для исполнения.
Примеры оптимизаций?
Отсечение колонок (projection pruning), проталкивание фильтров вниз (predicate pushdown), объединение узких операций, постоянное свёртывание выражений, переупорядочивание join. Всё это видно в explain().
Пример
df = spark.read.parquet("s3://bucket/events") \
    .filter(F.col("dt") == "2026-10-12") \
    .select("user_id", "amount")

df.explain("extended")
# == Parsed Logical Plan ==
# == Analyzed Logical Plan ==
# == Optimized Logical Plan ==   <- здесь видны правила Catalyst
# == Physical Plan ==
Вывод составителяКлючевая мысль: вы пишете декларативно, а Catalyst решает, как именно исполнять. Поэтому одинаковый результат можно получить кодом, который в одном случае читает гигабайты, а в другом — мегабайты.
04

Tungsten и когда нужен RDD

Почему DataFrame быстрый и когда опускаться на уровень ниже.

Что спросят
  • Что такое Tungsten?
  • Почему DataFrame экономит память и CPU?
  • Когда всё-таки нужен RDD?
Вопросы и ответы
Что такое Tungsten?
Это проект низкоуровневой оптимизации Spark: собственное управление памятью вне JVM-кучи (off-heap), компактное бинарное представление строк и генерация байткода (whole-stage codegen) вместо интерпретации выражений.
Что это даёт на практике?
Меньше нагрузки на GC, выше плотность данных в памяти и лучшая скорость CPU. Вместе с Catalyst это и делает DataFrame быстрее ручного RDD-кода в большинстве табличных задач.
Когда всё-таки RDD?
Когда нет структурной операции под вашу задачу: сложный кастомный обход элементов, нестандартное разбиение, работа с неструктурированными данными, или когда нужен точный контроль над партиционированием и отказоустойчивостью на уровне элементов.
Пример
rdd = spark.sparkContext.textFile("s3://bucket/log.txt")

# кастомный разбор, для которого нет простого DataFrame-оператора
errors = (
    rdd.filter(lambda line: "ERROR" in line)
       .map(lambda line: line.split("|"))
       .map(lambda parts: (parts[0], 1))
       .reduceByKey(lambda a, b: a + b)
)
errors.take(5)
Вывод составителяПравило: сначала попробуйте выразить задачу через DataFrame. RDD — запасной вариант, когда структура мешает. И даже тогда возвращайте DataFrame как можно раньше, чтобы вернуть себе оптимизации.
05

UDF и их цена

Обычный UDF против pandas_udf — и почему это важно.

Что спросят
  • Почему UDF считаются дорогими?
  • Чем pandas_udf лучше обычного UDF?
  • Когда UDF оправдан?
Вопросы и ответы
Чем плох обычный UDF?
Он исполняется вне оптимизатора: Catalyst не может заглянуть внутрь, а строки по одной сериализуются из JVM в Python и обратно. Это и мешает codegen, и резко снижает производительность на больших данных.
Что даёт pandas_udf?
Он работает векторизованно: принимает pandas.Series и обрабатывает данные пачками через Arrow, а не по строке. Накладные расходы на сериализацию падают в разы, и такой UDF заметно быстрее обычного.
Когда UDF оправдан?
Когда логику нельзя выразить встроенными функциями pyspark.sql.functions, а переносить её в SQL-выражение нецелесообразно. Всегда сначала проверьте встроенные функции — они оптимизируются.
Пример
from pyspark.sql.functions import udf, pandas_udf
from pyspark.sql.types import DoubleType
import pandas as pd

# обычный UDF: Python по строке, сериализация JVM <-> Python
@udf(DoubleType())
def norm(x):
    return None if x is None else x / 100.0

# pandas UDF: векторизованно, через Arrow, в разы быстрее
@pandas_udf(DoubleType())
def norm_vec(x: pd.Series):
    return x / 100.0

df.withColumn("amount_norm", norm_vec("amount"))
Частые ошибки
  • Пишут UDF там, где есть встроенная функция, и теряют оптимизацию.
  • Используют обычный UDF на больших объёмах, вместо pandas_udf.
  • Забывают типизировать возвращаемое значение или указывают неверный тип.
Вывод составителяФормулировка для интервью: «UDF разрывают оптимизатор и codegen, поэтому дороги; pandas_udf возвращает часть производительности за счёт векторизации». Сначала встроенные функции — и только потом свой код.
Итог

Общий вывод составителя

DataFrame и RDD — это не «старое» и «новое», а два уровня абстракции. RDD даёт контроль, DataFrame — оптимизацию через Catalyst и Tungsten. В табличных задачах почти всегда выигрывает DataFrame.

Явная схема и корректные типы — это фундамент: они снимают неопределённость, экономят память и не дают оптимизатору ошибиться. Catalyst превращает декларативный код в эффективный план, а Tungsten делает исполнение этого плана быстрым и экономичным по памяти.

UDF — последний инструмент. Сначала встроенные функции, затем pandas_udf для векторизации, и только при необходимости обычный UDF. Чем реже вы «ломаете» оптимизатор, тем быстрее и стабильнее ваш пайплайн.
