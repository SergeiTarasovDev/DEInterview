01

Broadcast Hash Join

Маленькую таблицу рассылаем, большую не shuffle-им.

Что спросят
  • Как работает broadcast hash join?
  • Когда Spark выбирает его автоматически?
  • Какие у него ограничения?
Вопросы и ответы
Как он работает?
Маленькая таблица целиком рассылается на все экзекьюторы и держится в памяти как хеш-таблица. Большая таблица обрабатывается локально, покартиционно, без shuffle. Это самый быстрый вариант соединения, когда применим.
Когда происходит автоматически?
Когда статистика показывает, что одна сторона меньше spark.sql.autoBroadcastJoinThreshold (по умолчанию около 10 МБ). Формально проверяется оценка размера, а не факт, поэтому оценка бывает неточной.
Ограничения?
Таблица должна влезать в память и драйвера, и каждого экзекьютора. Слишком большой «маленькой» стороны — OOM драйвера или экзекьюторов. Также плохо работает при FULL OUTER join, который требует согласованного партиционирования.
Пример
from pyspark.sql.functions import broadcast

# маленький справочник -> все экзекьюторы, без shuffle большой таблицы
result = big.join(broadcast(small_dict), "user_id", "left")

result.explain()
# BroadcastHashJoin [user_id], [user_id], LeftOuter
Частые ошибки
  • Насильно бродкастят таблицу, которая не влезает в память, — получают OOM.
  • Не понимают, что при broadcast большая таблица всё равно читается целиком.
  • Ожидают broadcast при full outer join.
Вывод составителяBroadcast — стратегия по умолчанию «по возможности»: убрать shuffle большой таблицы почти всегда выгоднее всего. Следите только за тем, чтобы маленькая сторона действительно была маленькой.
02

Sort-Merge Join

Стратегия для больших таблиц: сортировка и слияние.

Что спросят
  • Как работает sort-merge join?
  • Почему он выдерживает большие объёмы?
  • Когда он — стратегия по умолчанию?
Вопросы и ответы
Как он работает?
Обе стороны shuffle-ятся по ключу join, затем сортируются, а потом сливаются проходом по отсортированным последовательностям. Сортировка даёт предсказуемый доступ и позволяет обходиться без загрузки всей стороны в память.
Почему он масштабируется?
Потому что не требует держать одну таблицу целиком в памяти: работает по партициям отсортированных данных, используя и память, и диск. Это разумный выбор, когда обе таблицы большие.
Минусы?
Два shuffle и дорогая сортировка. Если ключей мало и присутствует перекос, одна партиция может стать непосильно большой. Поэтому sort-merge чувствителен к распределению ключей.
Пример
# обе таблицы большие -> sort-merge join по умолчанию
result = big_left.join(big_right, "user_id", "inner")

result.explain()
# SortMergeJoin [user_id], [user_id], Inner
# :- Sort ...            <- обе стороны сортируются
# +- Sort ...
Вывод составителяЕсли убрать всю специфику, идея такая: broadcast — не shuffle большого, sort-merge — корректно обработать два больших набора. Именно sort-merge чаще всего и запускается, когда обе таблицы большие.
03

Shuffle Hash Join

Хеш-таблица на партицию вместо сортировки.

Что спросят
  • Чем shuffle hash join отличается от sort-merge?
  • Когда он может быть выгоднее sort-merge?
  • Почему он реже включается?
Вопросы и ответы
Как он работает?
Обе стороны shuffle-ятся по ключу, после чего Spark строит хеш-таблицу по меньшей стороне и прогоняет через неё большую. Сортировка не нужна — отсюда потенциальный выигрыш.
Когда выгоден?
Когда одна сторона достаточно мала, чтобы построить по ней хеш-таблицу в памяти, но при этом не настолько мала для broadcast. Тогда экономится дорогая сортировка обеих сторон.
Почему редко включается?
По умолчанию в Spark 3 он отключён (spark.sql.join.preferSortMergeJoin=true), потому что требует, чтобы меньшая сторона партиции уверенно помещалась в память, иначе начнётся spill. Его включают осознанно через hint.
Пример
spark.sql("""
  SELECT /*+ SHUFFLE_HASH(a, b) */ *
  FROM orders a
  JOIN products b ON a.product_id = b.product_id
""")

# план покажет ShuffledHashJoin вместо SortMergeJoin
Вывод составителяНа интервью достаточно назвать нишу: «shuffle hash — компромисс между broadcast и sort-merge, когда одна сторона мала, но не помещается в память для рассылки». Не стоит углубляться дальше, если не спросят.
04

Как выбирается стратегия

Статистика, пороги и join hints.

Что спросят
  • По какому принципу Spark выбирает стратегию join?
  • Какие hint-ы есть и зачем они?
  • Почему оценка размера может ошибаться?
Вопросы и ответы
Как Spark выбирает?
По логике планировщика: если одна сторона меньше порога broadcast — broadcast hash join; иначе, при включённом shuffle hash и подходящем размере — shuffled hash; иначе — sort-merge. На решение влияет статистика (метаданные, размер файлов, каталог) и наличие hint.
Какие есть hints?
/*+ BROADCAST(t) */ — навязать broadcast, /*+ SHUFFLE_HASH(a, b) */ — shuffled hash, /*+ MERGE(a, b) */ — sort-merge, /*+ SHUFFLE_REPLICATE_NL(a, b) */ — replicated nested loop для неэкви-join. Есть и версии со стратегией соединения (BROADCAST/SHUFFLE_MERGE и т.д.).
Почему оценка размера врёт?
Spark опирается на статистику, которая может быть устаревшей или отсутствовать (например, после сложных выражений и UDF). Из-за этого он иногда бродкастит «маленькую» таблицу, которая по факту огромна. AQE и ANALYZE TABLE помогают поправить ситуацию.
Пример
# явные подсказки стратегии (Spark SQL)
spark.sql("""
  SELECT /*+ BROADCAST(d) */ *
  FROM events e JOIN dim d ON e.dim_id = d.id
""")

spark.sql("""
  SELECT /*+ MERGE(a, b) */ *
  FROM big_a a JOIN big_b b ON a.id = b.id
""")

# обновление статистики помогает планировщику
spark.sql("ANALYZE TABLE events COMPUTE STATISTICS")
Частые ошибки
  • Ставят hint, не проверив план через explain().
  • Ожидают, что hint всегда выиграет: неверный hint может ухудшить план.
  • Забывают обновлять статистику таблиц перед тяжёлыми join.
Вывод составителяHint — это подсказка, а не приказ оптимизатору в обход реальности. Правильный подход: сначала посмотреть план, понять, что не так, и только затем вмешаться подсказкой или AQE.
05

Перекос при join

Хот-ключи на сторонах соединения и способы их сгладить.

Что спросят
  • Почему join особенно чувствителен к перекосу?
  • Как справиться с перекосом при join?
  • Когда перекос появляется из-за NULL?
Вопросы и ответы
Почему join страдает от перекоса?
При shuffle обе стороны делятся по ключу. Если один ключ встречается у большинства строк, вся его доля попадает в одну партицию — одна задача обрабатывает почти весь объём, остальные простаивают.
Как с этим бороться?
По возрастанию сложности: убрать хот-ключи фильтром, если они не нужны; использовать broadcast, если одна сторона мала; включить AQE skew join; применить salting хот-ключа; в крайнем случае разделить хот-ключ и обработать отдельно.
При чём тут NULL?
NULL в ключе join не совпадает ни с чем (по правилам SQL), но все строки с NULL уходят в одну и ту же партицию. На больших объёмах это сама по себе огромная партиция, хотя полезного соединения не даёт.
Пример
from pyspark.sql import functions as F

# 1) отсечь бесполезные NULL до join
left = left.filter(F.col("user_id").isNotNull())

# 2) если один ключ-хот-ключ, можно вынести его отдельно
hot = left.filter(F.col("user_id") == 0)
rest = left.filter(F.col("user_id") != 0)

joined_rest = rest.join(dim, "user_id")          # без перекоса
joined_hot = hot.join(broadcast(dim), "user_id") # маленькая сторона -> broadcast
result = joined_rest.unionByName(joined_hot)
Вывод составителяПерекос при join — самая частая причина «зависшего» job в проде. Порядок действий запомните как алгоритм: фильтр, broadcast, AQE, и только потом ручной salting или вынос хот-ключа.
Итог

Общий вывод составителя

Три стратегии join — это три точки на шкале «сколько бы данных мы готовы возить по сети». Broadcast старается не shuffle-ить большую таблицу, sort-merge честно обрабатывает две большие стороны, shuffled hash ищет компромисс по памяти.

Выбор стратегии делает планировщик по статистике, а вы влияете на него hint-ами и AQE. Но помните главное: никакая стратегия не спасёт от перекоса. Хот-ключ превращает самую масштабируемую операцию в последовательную.

Уверенный Senior-ответ строится вокруг одного алгоритма: сначала убрать лишние данные и хот-ключи, затем попробовать broadcast, затем положиться на AQE, и только потом браться за salting. Так вы показываете и знание движка, и инженерное мышление.
