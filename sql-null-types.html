01

Природа NULL и трёхзначная логика

Почему = NULL не работает и что такое «неизвестно».

Что спросят
  • Что такое NULL — пустая строка, ноль или отсутствие значения?
  • Почему col = NULL не возвращает строки?
  • Что такое трёхзначная логика?
  • Чем IS DISTINCT FROM отличается от <>?
Вопросы и ответы
Что такое NULL?
NULL — это отсутствие значения, «неизвестно». Это не ноль, не пустая строка и не пробел. Ноль — конкретное число, пустая строка '' — конкретная строка нулевой длины, а NULL означает «значение неизвестно или не задано».
Почему col = NULL не работает?
Потому что результат сравнения с NULL — это не TRUE и не FALSE, а UNKNOWN. В WHERE остаются только строки, для которых условие TRUE. Поэтому для проверки на отсутствие значения используют IS NULL / IS NOT NULL.
Что такое трёхзначная логика?
Логика с тремя состояниями: TRUE, FALSE и UNKNOWN. Любая арифметика или сравнение с NULL даёт UNKNOWN. В WHERE UNKNOWN отбрасывается так же, как FALSE, — отсюда «пропавшие» строки.
IS DISTINCT FROM — зачем?
Обычное <> с NULL даёт UNKNOWN, и строки теряются. IS DISTINCT FROM считает NULL обычным сравнимым значением: 1 IS DISTINCT FROM NULL → TRUE, NULL IS DISTINCT FROM NULL → FALSE. Незаменимо при сверке данных.
Пример
-- не найдёт строк с NULL в phone
SELECT * FROM users WHERE phone = NULL;      -- пусто

-- правильно
SELECT * FROM users WHERE phone IS NULL;

-- безопасное сравнение «различаются ли», с учётом NULL
SELECT * FROM a JOIN b USING (id)
WHERE a.amount IS DISTINCT FROM b.amount;
Вывод составителяКак только вы перестаёте думать о NULL как о «значении» и начинаете думать как о «неизвестно», половина странного поведения SQL становится объяснимой.
02

Ловушка NOT IN

Почему NOT IN с NULL возвращает пустой результат.

Что спросят
  • Почему NOT IN с подзапросом может вернуть пусто?
  • Как обезопасить NOT IN?
  • Чем NOT EXISTS лучше NOT IN?
  • Как ведёт себя IN с NULL?
Вопросы и ответы
Почему NOT IN ломается о NULL?
Условие x NOT IN (1, 2, NULL) раскрывается в x <> 1 AND x <> 2 AND x <> NULL. Последнее даёт UNKNOWN. А UNKNOWN AND TRUE равно UNKNOWN, и вся строка отбрасывается. Если в подзапросе есть хотя бы один NULL, результат будет пустым.
Как обезопасить NOT IN?
Либо добавить WHERE col IS NOT NULL в подзапрос, либо, что надёжнее, заменить на NOT EXISTS — он корректно обрабатывает NULL и не зависит от пропусков.
IN с NULL ведёт себя иначе?
IN тоже даёт UNKNOWN при сравнении с NULL, но здесь это не так опасно: строка найдётся, если совпадёт хотя бы с одним непустым значением. Проблема появляется именно с NOT IN.
Пример
-- ПЛОХО: если в orders.client_id есть NULL, результат будет пуст
SELECT * FROM clients
WHERE client_id NOT IN (SELECT client_id FROM orders);

-- ХОРОШО: NOT EXISTS корректно обрабатывает NULL
SELECT * FROM clients c
WHERE NOT EXISTS (
  SELECT 1 FROM orders o WHERE o.client_id = c.client_id
);

-- либо явно исключить NULL в подзапросе
SELECT * FROM clients
WHERE client_id NOT IN (
  SELECT client_id FROM orders WHERE client_id IS NOT NULL
);
Частые ошибки
  • Отлаживают пустой результат запроса, не подозревая, что в подзапросе есть NULL.
  • «Починивают» через COALESCE на стороне левой таблицы — это не решает проблему NULL в правой.
  • Считают, что NOT IN и NOT EXISTS всегда взаимозаменяемы.
Вывод составителяЗапомните как рефлекс: увидели NOT IN — ищите NULL. На интервью этот вопрос очень любят именно потому, что ответ короткий, а ошибка — тихая.
03

Агрегаты, COALESCE, NULLIF

NULL в COUNT/SUM/AVG, подстановка значений и деление на ноль.

Что спросят
  • Как NULL влияет на COUNT, SUM, AVG?
  • Что делает COALESCE и чем он отличается от NULLIF?
  • Как безопасно делить, избегая деления на ноль?
  • Что вернёт SUM на пустой выборке?
Вопросы и ответы
NULL в COUNT/SUM/AVG?
COUNT(*) считает все строки. COUNT(col) игнорирует NULL. SUM и AVG тоже пропускают NULL, причём AVG делит на количество непустых значений — среднее может оказаться неожиданно высоким.
COALESCE vs NULLIF?
COALESCE(a, b, ...) возвращает первое непустое значение — используется для подстановки. NULLIF(a, b) возвращает NULL, если a = b, иначе a — используется, чтобы превратить «нежелательное» значение (например ноль) в NULL.
Как безопасно делить?
Обернуть знаменатель в NULLIF: a / NULLIF(b, 0). Если b = 0, знаменатель станет NULL, и результат тоже будет NULL — без ошибки деления на ноль. Дальше при необходимости подставить запасное значение через COALESCE.
SUM на пустой выборке?
NULL. Это сюрприз для многих: ожидают ноль. Оборачивайте в COALESCE(SUM(x), 0). Исключение — COUNT, который на пустой выборке возвращает 0.
Пример
SELECT
  COUNT(*)                              AS rows_total,
  COUNT(amount)                         AS amount_filled,
  AVG(amount)                           AS avg_filled,
  COALESCE(SUM(amount), 0)              AS total_safe,
  COALESCE(amount, 0)                   AS amount_zero,
  NULLIF(discount, 0)                   AS discount_or_null,
  revenue / NULLIF(orders_cnt, 0)       AS avg_check
FROM sales;
Частые ошибки
  • Делят без защиты и получают ошибку division by zero или «бесконечность».
  • Ожидают ноль от SUM и AVG на пустых данных.
  • Путают направления: ставят NULLIF там, где нужен COALESCE, и наоборот.
Вывод составителяДва инструмента, которые стоит держать под рукой: COALESCE — «дай первое непустое», NULLIF — «преврати в NULL». В связке они закрывают и подстановку значений, и безопасное деление.
04

Типы данных, даты и таймзоны

int, decimal, float, даты и опасность неявных приведений.

Что спросят
  • Чем DECIMAL отличается от FLOAT и почему для денег берут DECIMAL?
  • Чем TIMESTAMP отличается от TIMESTAMPTZ?
  • Чем опасны неявные приведения типов?
  • Как сравнивать даты корректно?
Вопросы и ответы
DECIMAL vs FLOAT?
FLOAT — число с плавающей точкой, хранит приближение, и на нём 0.1 + 0.2 может не дать ровно 0.3. DECIMAL(p, s) — точное десятичное число с заданной точностью. Для денег и любых точных расчётов берут DECIMAL/NUMERIC, никогда не FLOAT.
TIMESTAMP vs TIMESTAMPTZ?
TIMESTAMP хранит дату и время без часового пояса — «настенное» время. TIMESTAMPTZ хранит момент времени и нормализует его к UTC. Для событий используйте TIMESTAMPTZ, иначе при смене таймзоны сервера данные «поедут».
Чем опасны неявные приведения?
База может молча привести тип и получить неожиданный результат или сломать индекс. Пример: сравнение строки с числом, где '10' < '9' как строки, но 10 > 9 как числа. Ещё хуже, когда приведение делается к колонке — это скрытая функция и потеря sargability.
Как сравнивать даты?
Не приводить дату к строке. Сравнивать в диапазоне: created_at >= '2024-01-01' AND created_at < '2024-02-01'. Так вы избегаете и проблем с форматом, и лишних функций над колонкой.
Пример
-- ПЛОХО для денег: приближение
SELECT 0.1::float8 + 0.2::float8;   -- 0.30000000000000004

-- ХОРОШО: точные деньги
SELECT 0.1::numeric + 0.2::numeric; -- 0.3

-- ПЛОХО: неявное приведение, возможна потеря строк
SELECT * FROM events WHERE event_date = '01.02.2024';

-- ХОРОШО: диапазон по дате, без функций над колонкой
SELECT * FROM events
WHERE event_date >= '2024-02-01' AND event_date < '2024-03-01';
Частые ошибки
  • Считают деньги в FLOAT и потом ловят копеечные расхождения в отчётах.
  • Хранят события в TIMESTAMP без пояса и путаются при агрегации по дням.
  • Сравнивают дату со строкой в «человеческом» формате, получая неполную выборку.
Вывод составителяТип данных — это часть логики, а не деталь. Деньги — DECIMAL, события — TIMESTAMPTZ со сравнением диапазоном. Тогда ни округление, ни таймзоны не испортят метрику задним числом.
05

Задачи с решениями

Типовые вопросы, где NULL меняет ответ.

Задача 1. Заменить NULL на значение по умолчанию
SELECT
  client_id,
  COALESCE(city, 'не указан') AS city
FROM clients;

-- несколько вариантов подстановки по приоритету
SELECT COALESCE(mobile, work_phone, home_phone, 'нет телефона') AS phone
FROM contacts;

COALESCE берёт первое непустое значение слева направо — удобно для «запасных» источников.

Задача 2. Среднее, устойчивое к пропускам и нулям
SELECT
  AVG(rating)                       AS avg_all_filled,
  AVG(COALESCE(rating, 0))          AS avg_zero_filled
FROM reviews;

-- среднее только по строкам, где оценка реально есть
SELECT AVG(rating) AS avg_rated
FROM reviews
WHERE rating IS NOT NULL;
Задача 3. Безопасное деление (конверсия)
SELECT
  visits,
  orders,
  orders / NULLIF(visits, 0) AS conversion
FROM funnel;

Без NULLIF строка с нулевыми визитами уронила бы запрос делением на ноль.

Задача 4. Найти записи, которых нет, без ловушки NOT IN
SELECT c.client_id
FROM clients c
WHERE NOT EXISTS (
  SELECT 1 FROM orders o WHERE o.client_id = c.client_id
);

Если в orders.client_id есть NULL, вариант с NOT IN вернул бы пусто.

Задача 5. Сверка двух таблиц с учётом NULL
SELECT a.id, a.amount AS src, b.amount AS tgt
FROM source a
FULL OUTER JOIN target b USING (id)
WHERE a.amount IS DISTINCT FROM b.amount;

IS DISTINCT FROM считает NULL полноценным значением — строки с расхождением не теряются.

Вывод составителяВ каждой из этих задач правильное решение отличается от «наивного» ровно обработкой NULL. Проговаривайте на интервью, почему выбран COALESCE, NULLIF или NOT EXISTS — это и есть проверка понимания темы.
Итог

Общий вывод составителя

NULL и типы данных — это тихая тема: ошибки здесь не роняют запрос, а незаметно меняют ответ. Именно поэтому её так любят на собеседованиях. Три опоры, которые стоит довести до автоматизма: NULL — это UNKNOWN, а не значение; сравнение с NULL требует IS NULL и IS DISTINCT FROM; агрегаты игнорируют NULL и могут дать неожиданный результат.

Два инструмента закрывают большинство практических кейсов: COALESCE для подстановки и NULLIF для безопасного деления и превращения «плохих» значений в NULL. А привычка писать NOT EXISTS вместо NOT IN снимает целый класс ошибок с пропавшими строками.

И не забывайте про типы: деньги — DECIMAL, события — TIMESTAMPTZ, даты сравниваем диапазоном. Большая часть «загадочных» расхождений в отчётах — это либо NULL, либо неявное приведение типа.
