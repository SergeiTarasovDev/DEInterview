01

Компоненты кластера

Driver, executors, cluster manager — кто за что отвечает.

Что спросят
  • Чем driver отличается от executor?
  • Где выполняется код пользователя, а где — сама обработка данных?
  • Какую роль играет cluster manager?
Вопросы и ответы
Driver и executors — в чём разница?
Driver — управляющий узел: он запускает main(), строит план выполнения, планирует задачи и собирает результаты. Executors — рабочие JVM-процессы на воркерах: они держат данные в памяти и выполняют сами задачи. Драйвер оркестрирует, экзекьюторы считают.
Что делает cluster manager?
Выделяет ресурсы кластера под приложение: стартует executors, следит за их жизнеспособностью. Это может быть Standalone, YARN, Kubernetes или Mesos. Spark умеет работать с любым из них через один и тот же API.
В каком режиме выполняется приложение?
В client mode драйвер живёт на машине, откуда отправлена команда (удобно для отладки, но канал связи нестабилен). В cluster mode драйвер запускается внутри кластера (устойчивее, стандарт для продакшена).
  • Драйвер — единая точка отказа: упал драйвер — упало всё приложение.
  • Executors независимы друг от друга и не общаются напрямую — только через драйвер и shuffle-сервис.
  • Данные в экзекьюторах живут в памяти и на локальном диске (spill), а не на драйвере.
Вывод составителяФормулировка, которая нравится интервьюерам: «драйвер планирует, экзекьюторы исполняют, а cluster manager выдаёт ресурсы». Дальше уже можно детализировать по режимам запуска.
02

Ленивые трансформации и действия

Почему ничего не считается, пока не вызвано действие.

Что спросят
  • Чем трансформация отличается от действия?
  • Почему filter и select не запускают вычисления?
  • Что такое ленивые вычисления и зачем они нужны?
Вопросы и ответы
Трансформация vs действие?
Трансформации (select, filter, withColumn, join) только описывают, что нужно сделать, и возвращают новый DataFrame/RDD. Действия (count, collect, show, write, foreach) инициируют реальное вычисление и возвращают результат.
Зачем нужна ленивость?
Она даёт оптимизатору полную картину пайплайна. Spark видит всю цепочку и может объединить операции, отсечь ненужные колонки, поменять порядок фильтров и выбрать лучшую стратегию join. Плюс не выполняется работа, результат которой никто не запросил.
Пример
from pyspark.sql import SparkSession
from pyspark.sql import functions as F

spark = (
    SparkSession.builder
    .appName("demo")
    .config("spark.executor.memory", "8g")
    .getOrCreate()
)

df = (
    spark.read.parquet("s3://bucket/events")
    .filter(F.col("dt") == "2026-10-12")   # лениво
    .select("user_id", "event")            # лениво
)

# до этой строки не выполнено ни одной задачи
df.groupBy("event").count().show()         # действие запускает job
Частые ошибки
  • Ждут, что после трансформации файлы уже прочитаны, — а физического чтения ещё нет.
  • Многократно вызывают действия на одном DataFrame без cache, пересчитывая весь пайплайн заново.
  • Путают count() (действие) и select() (трансформация) по «весу» операции.
Вывод составителяПростой тест на понимание: спросите себя, «поедут ли данные по сети прямо сейчас». Если нет — это трансформация. Отсюда же растёт тема оптимизации и Catalyst.
03

Job, stage, task

Иерархия работы: как действие превращается в параллельные задачи.

Что спросят
  • Какие уровни выполнения есть в Spark?
  • Сколько задач в одной стадии?
  • Почему стадии разделяются именно на shuffle?
Вопросы и ответы
Иерархия job/stage/task?
Job — одно действие (например count). Внутри job строится DAG, который разбивается на stages по границам shuffle. Каждая стадия состоит из tasks — по одной на партицию данных. Task — минимальная единица работы, которую выполняет один executor-поток.
Сколько задач в стадии?
Число задач равно числу партиций на входе стадии. Уменьшили партиции coalesce — уменьшили и параллелизм. Поэтому «один огромный файл» часто приводит к стадии из одной задачи.
Почему граница стадии — это shuffle?
Потому что после shuffle данные нужно полностью материализовать и перераспределить по сети, прежде чем начать следующую стадию. До shuffle всё можно считать в одном проходе (pipeline), после — нужен барьер.
Пример
df = spark.read.parquet("s3://bucket/events")

df.groupBy("country").count().explain(True)

# == Physical Plan ==
# * HashAggregate ...            <- partial (до shuffle)
#   Exchange ...                 <- граница стадии (shuffle)
# * HashAggregate ...            <- final (после shuffle)
Вывод составителяЗапомните связку: 1 действие = 1 job, 1 shuffle = +1 stage, 1 партиция = 1 task. На этих трёх правилах держится чтение Spark UI.
04

DAG и SparkSession

Граф вычислений и точка входа в приложение.

Что спросят
  • Что такое DAG и зачем он нужен?
  • Почему Spark строит граф, а не выполняет строку за строкой?
  • Зачем нужен SparkSession?
Вопросы и ответы
Что такое DAG?
Directed Acyclic Graph — направленный ациклический граф: вершины это данные (RDD/DataFrame), рёбра — трансформации. Граф не содержит циклов, поэтому порядок вычисления детерминирован. По DAG драйвер строит физический план и разбивает его на стадии.
Почему граф, а не императивно?
Граф позволяет оптимизировать весь пайплайн целиком: объединять операции, менять порядок, переиспользовать вычисленные партиции. Императивное выполнение такой свободы не даёт.
Зачем SparkSession?
Это единая точка входа с Spark 2.x: заменяет SparkContext, SQLContext и HiveContext. Через неё читают данные, выполняют SQL, настраивают конфигурации. SparkContext спрятан внутри и доступен как spark.sparkContext.
Пример
from pyspark.sql import SparkSession

spark = (
    SparkSession.builder
    .appName("dag-demo")
    .config("spark.sql.shuffle.partitions", "200")
    .getOrCreate()
)

# SQL и DataFrame API работают с одним движком
spark.sql("SELECT 1 AS one").show()
print(spark.sparkContext.appName)
Вывод составителяDAG — это «черновик» вычислений, который оптимизатор доводит до физического плана. Если кандидат умеет показать план через explain() и объяснить границы стадий, тема закрыта.
05

Narrow и wide трансформации

Когда данные едут по сети, а когда нет.

Что спросят
  • Чем narrow-трансформация отличается от wide?
  • Какие операции вызывают shuffle?
  • Почему широкие трансформации дороже?
Вопросы и ответы
Narrow vs wide?
Narrow — каждая входная партиция нужна максимум одной выходной, данные не переезжают между узлами (select, filter, withColumn, map). Wide — выходная партиция зависит от многих входных, требуется shuffle (groupBy, join, orderBy, distinct, repartition).
Почему wide дороже?
Данные пишутся на диск, передаются по сети, сортируются и объединяются. Это сетевая и дисковая нагрузка плюс сериализация. Каждый shuffle — потенциальные точки перекоса и spill.
Почему narrow-операции объединяются в одну стадию?
Их можно применять к каждой партиции независимо, одной задачей. Spark выстраивает их в pipeline и не создаёт барьеров, пока не встретит wide-операцию.
Пример
# narrow: не тянет shuffle
df.select("user_id").filter(F.col("user_id").isNotNull())

# wide: тянет shuffle
df.groupBy("country").agg(F.sum("revenue"))
df.orderBy(F.desc("revenue"))
df.join(other, "user_id")
Частые ошибки
  • Недооценивают orderBy — это всегда дорогая wide-операция.
  • Ставят repartition «на всякий случай», добавляя лишний shuffle.
  • Путают distinct (shuffle) и dropDuplicates на маленьких объёмах, ожидая одинакового плана.
Вывод составителяКлючевой вопрос самопроверки: «нужны ли данные конкретной партиции другим партициям?» Если да — это wide, и дальше начинается тема партиционирования и shuffle.
Итог

Общий вывод составителя

Архитектура Spark держится на нескольких опорах: драйвер планирует, экзекьюторы считают, cluster manager выдаёт ресурсы. Вычисления ленивы по определению — от трансформации до действия пайплайн остаётся лишь описанием.

Из ленивости вырастает вся иерархия исполнения: действие порождает job, DAG режется на stages по границам shuffle, а каждая стадия раскладывается на tasks по числу партиций. Понимание narrow/wide — это то, чем вы объясняете, почему одни операции дешёвые, а другие тянут данные по сети.

На интервью старайтесь не просто перечислять компоненты, а показывать причинно-следственные связи: ленивость даёт оптимизатору свободу, широкая трансформация создаёт барьер, барьер рождает стадию. Именно этот «рассказ по цепочке» отличает подготовленного кандидата.
