01

Top-N на группу и дедупликация

Классика с оконными функциями.

Задача 1. Топ-3 товара по выручке в каждой категории

Нумеруем строки внутри категории по убыванию выручки и оставляем первые три во внешнем запросе, потому что фильтровать окно в WHERE нельзя.

WITH ranked AS (
  SELECT
    category_id,
    product_id,
    revenue,
    ROW_NUMBER() OVER (
      PARTITION BY category_id
      ORDER BY revenue DESC, product_id
    ) AS rn
  FROM product_revenue
)
SELECT category_id, product_id, revenue
FROM ranked
WHERE rn <= 3
ORDER BY category_id, rn;
Задача 2. Дедупликация: оставить самую свежую запись

Если нужна ровно одна строка на ключ — ROW_NUMBER. Если нужны все строки-победители при равных датах — RANK.

SELECT *
FROM (
  SELECT
    *,
    ROW_NUMBER() OVER (
      PARTITION BY user_id
      ORDER BY updated_at DESC, id DESC
    ) AS rn
  FROM users_raw
) t
WHERE rn = 1;
Частые ошибки
  • Пытаются отфильтровать номер строки в том же SELECT — нужен CTE или подзапрос.
  • Не добавляют второй ключ сортировки — при равных датах результат «плавает» между запусками.
  • Берут RANK для топ-N, ожидая ровно N строк, а получают больше при равенстве значений.
Вывод составителяФормула «нумеруем внутри группы → фильтруем снаружи» закрывает и top-N, и дедупликацию. Проговаривайте её вслух — интервьюер оценивает ход мысли.
02

Воронка конверсии

Сколько пользователей доходит до каждого шага.

Задача. Воронка: визит → регистрация → заказ → оплата

Считаем уникальных пользователей на каждом шаге и конверсию относительно первого шага. Используем условную агрегацию, чтобы получить все шаги за один проход.

SELECT
  COUNT(DISTINCT CASE WHEN step = 'visit'    THEN user_id END) AS visits,
  COUNT(DISTINCT CASE WHEN step = 'signup'   THEN user_id END) AS signups,
  COUNT(DISTINCT CASE WHEN step = 'order'    THEN user_id END) AS orders,
  COUNT(DISTINCT CASE WHEN step = 'paid'     THEN user_id END) AS paid,
  ROUND(
    COUNT(DISTINCT CASE WHEN step = 'paid' THEN user_id END) * 100.0
    / NULLIF(COUNT(DISTINCT CASE WHEN step = 'visit' THEN user_id END), 0)
  , 2) AS paid_conversion_pct
FROM events;

Если у пользователя может быть несколько событий на шаге, DISTINCT обязателен — иначе один активный пользователь раздувает воронку. Помните, что воронка «засчитывает» шаг всем, кто его сделал, даже если порядок событий не соблюдён; для строгой последовательности нужно дополнительно проверять, что шаг случился после предыдущего.

Строгая воронка: шаг только после предыдущего
WITH steps AS (
  SELECT
    user_id,
    MIN(CASE WHEN step = 'visit'  THEN ts END) AS t_visit,
    MIN(CASE WHEN step = 'signup' THEN ts END) AS t_signup,
    MIN(CASE WHEN step = 'paid'   THEN ts END) AS t_paid
  FROM events
  GROUP BY user_id
)
SELECT
  COUNT(*) FILTER (WHERE t_visit IS NOT NULL)                    AS visits,
  COUNT(*) FILTER (WHERE t_signup >= t_visit)                    AS signups,
  COUNT(*) FILTER (WHERE t_paid   >= t_signup)                   AS paid
FROM steps;
Вывод составителяУточняющий вопрос «считать событие в любом порядке или строго по цепочке» показывает Senior-уровень: он сразу видит, что «плоская» воронка и «строгая» дают разные числа.
03

Retention по когортам

Возвращаемость пользователей по месяцам первой активности.

Задача. Retention по месячным когортам

Сначала определяем когорту — месяц первой активности пользователя. Затем «разворачиваем» активность в номер месяца относительно когорты и считаем долю вернувшихся.

WITH first_seen AS (
  SELECT
    user_id,
    MIN(DATE_TRUNC('month', activity_date)) AS cohort_month
  FROM activity
  GROUP BY user_id
),
activity_flag AS (
  SELECT DISTINCT
    a.user_id,
    f.cohort_month,
    DATE_TRUNC('month', a.activity_date) AS activity_month
  FROM activity a
  JOIN first_seen f USING (user_id)
),
cohort_size AS (
  SELECT cohort_month, COUNT(*) AS users
  FROM first_seen
  GROUP BY cohort_month
)
SELECT
  af.cohort_month,
  DATEDIFF('month', af.cohort_month, af.activity_month) AS month_no,
  COUNT(DISTINCT af.user_id) AS active_users,
  cs.users AS cohort_users,
  ROUND(COUNT(DISTINCT af.user_id) * 100.0 / cs.users, 2) AS retention_pct
FROM activity_flag af
JOIN cohort_size cs USING (cohort_month)
GROUP BY af.cohort_month, month_no, cs.users
ORDER BY af.cohort_month, month_no;

Ключевые детали: когорта вычисляется один раз по первой активности; месяц активности сравнивается с когортой через DATEDIFF; знаменатель — размер когорты, а не число активных в месяце. Без DISTINCT по user_id за месяц метрика завышается.

Частые ошибки
  • Считают когорту по последней активности или пересчитывают на каждом шаге — таблица «плывёт».
  • Делят на число активных пользователей вместо размера когорты.
  • Забывают DISTINCT: один пользователь с несколькими сессиями считается многократно.
Вывод составителяRetention — это всегда «когорта × период». Сформулируйте для интервьюера, что такое когорта (месяц первой активности) и что стоит в числителе и знаменателе, — и задача превращается в технику.

Gaps and islands и пропущенные id

Непрерывные интервалы и дыры в последовательностях.

Задача 1. Gaps and islands: серии непрерывных дат

Трюк в том, что от даты вычитается её номер по порядку. Внутри непрерывного «острова» разность постоянна — по ней и группируем.

WITH numbered AS (
  SELECT
    user_id,
    activity_date,
    activity_date - INTERVAL '1 day' * ROW_NUMBER() OVER (
      PARTITION BY user_id
      ORDER BY activity_date
    ) AS grp
  FROM (
    SELECT DISTINCT user_id, activity_date FROM activity
  ) d
)
SELECT
  user_id,
  MIN(activity_date) AS start_date,
  MAX(activity_date) AS end_date,
  COUNT(*)           AS length_days
FROM numbered
GROUP BY user_id, grp
ORDER BY user_id, start_date;
Задача 2. Поиск пропущенных id

Сравниваем существующие значения с полным диапазоном и находим дыры через LEAD — расстояние между соседними id больше единицы означает пропуск.

-- пропуски внутри диапазона id
SELECT
  id AS gap_start,
  next_id - 1 AS gap_end,
  next_id - id - 1 AS missing_count
FROM (
  SELECT
    id,
    LEAD(id) OVER (ORDER BY id) AS next_id
  FROM items
) t
WHERE next_id IS NOT NULL
  AND next_id - id > 1;

Для «универсального» решения без опоры на LEAD можно сгенерировать полный ряд (через generate_series или календарную таблицу) и найти значения, которых нет в основной таблице, через anti-join.

Частые ошибки
  • Забывают DISTINCT по датам — дубликаты ломают нумерацию и «острова» рвутся.
  • Считают разность типов некорректно (дата минус число в разных СУБД работает по-разному).
  • Ищут пропуски NOT IN вместо anti-join — риск NULL и медленный план.
Вывод составителяGaps and islands — это один приём: «дата минус row_number». Научитесь выводить его на доске с примером из пяти строк — и вопрос закрыт для любого набора данных.
05

Иерархия и running total

Обход дерева через self-join и нарастающие итоги.

Задача 1. Иерархия сотрудников: путь до руководителя

Рекурсивный CTE разворачивает дерево: начинаем с корня (где manager_id IS NULL) и на каждом шаге присоединяем подчинённых, накапливая путь.

WITH RECURSIVE org AS (
  SELECT
    id,
    name,
    manager_id,
    1 AS level,
    name::text AS path
  FROM employees
  WHERE manager_id IS NULL

  UNION ALL

  SELECT
    e.id,
    e.name,
    e.manager_id,
    o.level + 1,
    o.path || ' / ' || e.name
  FROM employees e
  JOIN org o ON e.manager_id = o.id
)
SELECT id, name, level, path
FROM org
ORDER BY path;

Базовый случай — корень, рекурсивная часть — подчинённые. level даёт глубину, path — человекочитаемый маршрут. Обязательно предусмотрите защиту от циклов в реальных данных.

Задача 2. Нарастающий итог и доля от общего

Нарастающий итог — сумма с ORDER BY и рамкой по умолчанию. Доля считается делением на общий итог, который берётся окном без ORDER BY.

SELECT
  day,
  amount,
  SUM(amount) OVER (ORDER BY day) AS running_total,
  SUM(amount) OVER ()             AS grand_total,
  ROUND(
    SUM(amount) OVER (ORDER BY day) * 100.0
    / NULLIF(SUM(amount) OVER (), 0)
  , 2) AS running_share_pct
FROM daily_sales
ORDER BY day;

Обратите внимание: оконная сумма с ORDER BY нарастает, а без него — это итог по всей выборке. Отсюда и получается кумулятивная доля. NULLIF защищает от деления на ноль на пустых данных.

Частые ошибки
  • Забывают базовый случай в рекурсивном CTE — запрос не завершается или возвращает пусто.
  • Не ограничивают глубину рекурсии — в данных с циклом запрос уходит в бесконечность.
  • Берут SUM(...) OVER () там, где нужен нарастающий итог, — получают константу вместо кумуляции.
Вывод составителяДва разных инструмента: иерархия — это WITH RECURSIVE, нарастающий итог — это окно с ORDER BY. Не смешивайте их: дерево нельзя развернуть оконной функцией, а running total не нужен рекурсивный CTE.

Общий вывод составителя

Все задачи этого раздела — это небольшая библиотека шаблонов: «нумеруем внутри группы → фильтруем снаружи» (top-N, дедупликация), «условная агрегация с DISTINCT» (воронка), «когорта × период» (retention), «дата минус row_number» (gaps and islands), «WITH RECURSIVE» (иерархия) и «SUM OVER (ORDER BY ...)» (running total). Узнавайте в новой формулировке знакомый каркас.

На собеседовании ценят не скорость написания кода, а проговаривание допущений: уникален ли ключ, нужен ли строгий порядок событий, что считать знаменателем метрики, могут ли быть NULL и дубликаты. Именно эти уточнения отличают Middle от Senior.

Практикуйтесь решать каждую задачу двумя способами — через окно и через self-join или подзапрос — и объяснять, какой из них вы предпочтёте и почему. Такой разговор показывает и глубину, и инженерную зрелость.
